# Phase 2 Technical Summary Report

This report summarizes the data validation, leakage safeguards, data splitting, feature engineering, and preprocessing architectures implemented for Phase 2 of the Capstone project.

---

## 1. Machine Learning Task Definitions
*   **CAML (Freshwater Ecosystems):**
    *   **Recommended Task:** Multiclass Classification of Bloom Severity.
    *   **Target Variable:** `severity` (integers 1 to 5).
    *   **Scientific Goal:** Predict the risk level of blue-green algae blooms using geographical, spatial, and temporal conditions without exposing biological counts.
*   **HABSOS (Marine Ecosystems):**
    *   **Recommended Task:** Multiclass Classification of Harmful Algal Bloom Category.
    *   **Target Variable:** `CATEGORY` ('not observed', 'very low', 'low', 'medium', 'high').
    *   **Scientific Goal:** Predict red tide category based on physical environmental sensors and coordinates.

---

## 2. Feature Selection & Leakage Mitigation

### Excluded Features and Reasons:
- `abun` (CAML) and `CELLCOUNT` (HABSOS): **Excluded as features** because they deterministically define the targets, causing severe target leakage.
- `CELLCOUNT_QA`, `SALINITY_QA`, `WATER_TEMP_QA`, `WIND_DIR_QA`, `WIND_SPEED_QA` (HABSOS): **Dropped** as they are administrative post-collection quality descriptors not available during real-time IoT inference.
- `uid`, `OBJECTID`: **Dropped** database keys.
- `GENUS`, `SPECIES`, `CELLCOUNT_UNIT`: **Dropped** constant features.
- `WIND_DIR`, `WIND_SPEED`: **Dropped** due to $>99\%$ missing values.

### Retained Input Feature Schema:
*   *CAML Inputs:* `lat` (latitude), `lon` (longitude), `distance_to_water_m`, `region`, `Season`, `Year`, `Month_sin`, `Month_cos`, `DayOfYear_sin`, `DayOfYear_cos`.
*   *HABSOS Inputs:* `LATITUDE`, `LONGITUDE`, `STATE_ID`, `SAMPLE_DEPTH`, `SALINITY`, `WATER_TEMP`, `Season`, `Year`, `Month_sin`, `Month_cos`, `DayOfYear_sin`, `DayOfYear_cos`, `SALINITY_is_missing`, `WATER_TEMP_is_missing`.

---

## 3. Data Partitioning & Splitting Strategy
To evaluate generalizability under temporal progression and prevent chronological autocorrelation leakage, we partitioned data strictly by date:
- **CAML Split Boundaries:**
  - **Train set:** Before 2020-01-01 ($19,038$ rows).
  - **Val set:** 2020-01-01 to 2020-12-31 ($2,252$ rows).
  - **Test set:** On or after 2021-01-01 ($2,280$ rows).
- **HABSOS Split Boundaries:**
  - **Train set:** Before 2021-01-01 ($185,720$ rows).
  - **Val set:** 2021-01-01 to 2022-12-31 ($18,494$ rows).
  - **Test set:** On or after 2023-01-01 ($7,620$ rows).

---

## 4. Preprocessing Architecture
We built custom scikit-learn compatible preprocessors and serialized them as pipeline assets under `models/`:
1.  **Temporal Feature Engineering:** Extracts Year, Month, Day, Season, and cyclic coordinates ($\sin$ & $\cos$ of Month and Day of Year) to represent cyclic seasonality.
2.  **Depth Imputation:** Fills null `SAMPLE_DEPTH` with $0.0$ meters per NOAA collection rules.
3.  **Group-Based Median Imputation (`GroupMedianImputer`):** Missing values in `SALINITY` and `WATER_TEMP` (~49%) are filled using the median value of the coordinate-time group (`STATE_ID` + `Month`) calculated strictly on training data.
4.  **Column Scaling & Encoding:** Continuous features are scaled using `StandardScaler`. Categorical features are encoded using `OneHotEncoder`. Unneeded identifiers are dropped.

---

## 5. Future IoT Virtual Sensor Alignment
At live prediction time, physical sensor nodes report:
- `temp` $\rightarrow$ feeds Model B `WATER_TEMP`.
- `salinity` $\rightarrow$ feeds Model B `SALINITY` (and triggers the Dynamic Routing Engine).
- `depth` $\rightarrow$ feeds Model B `SAMPLE_DEPTH`.
- `lat` / `lon` $\rightarrow$ feeds GPS coordinate inputs for both models.
- `RTC` $\rightarrow$ computes month/season parameters.

**Dynamic Routing logic:**
- Salinity $< 5$ PPT $\rightarrow$ route inputs to Model A (freshwater).
- Salinity $\ge 5$ PPT $\rightarrow$ route inputs to Model B (marine).

---

## 6. Limitations & Assumptions
- **Constant Coordinates:** For a stationary IoT sensor node, GPS coordinates and `distance_to_water_m` remain constant, making Month/Season and temperature/salinity the primary dynamic model inputs.
- **pH, Turbidity, and Dissolved Oxygen:** Although these simulated parameters will be generated by our ESP32 IoT node in later phases, they are absent from the historical scientific dataset. The backend will parse them but they cannot be used by the ML classifier inputs.

---

## 7. Recommended Recommendation for Phase 3 (Model Training)
For Model Training in Phase 3, we recommend evaluating the following multiclass modeling algorithms:
1.  **Baseline Classifier:** `LogisticRegression` (with L2 regularization) and `DecisionTreeClassifier` (for structural explainability).
2.  **Ensemble Classifiers:** `RandomForestClassifier` (extremely robust to outliers) and `GradientBoostingClassifier` / `LightGBM` (designed for high-dimensional tabular datasets).
3.  **Metrics for Evaluation:**
    *   F1-Score (macro-average) and Cohen's Kappa (due to class imbalances).
    *   **False Negative Rate (FNR) Audit:** In an aquatic warning gateway, predicting a critical bloom as normal (false negative) is catastrophic. We will select the final model that minimizes FNR for warning/critical classes.
